## 这个工具解决什么问题

你让 AI 改一个小功能，它动了九个文件。现在项目起不来了，撤销已经撤到头，你也想不起来一小时前登录页长什么样。

git 能解决这个问题。但 git 的前提是：你早就知道有 git 这回事、在东西没坏之前记得提交过、并且在你最没心情学东西的那一刻知道 `HEAD~3` 是什么意思。

timeloom 替你把快照拍了，不管你有没有记得。

```bash
timeloom restore healthy
```

这条命令把所有文件退回到**上一个真正能跑起来的版本**。哪怕你这辈子没提交过一次 commit，它也能用。

## 三步开始

```bash
npx timeloom init
```

```bash
npx timeloom watch
```

开一个终端让它一直跑着，就配置完了。

出事的时候：

```bash
npx timeloom restore healthy
```

想看图形界面：

```bash
npx timeloom watch --ui
```

## 和别的工具有什么不一样

**它知道哪些版本是能跑的。** timeloom 会在快照之后偷偷跑一遍你的构建（或者类型检查、lint），把结果记下来。所以 `restore healthy` 的含义不是「一小时前」，而是**上一个编译通过的版本**。这一点是这类工具里独一份的，它把「到底是什么时候坏的」这个让人抓狂的问题，变成了一条命令。

**它用人话描述改动。** 不是 `a3f9c2e — 7 files changed`，而是 `修改 3 个文件，位于 src/components · 界面`。快照会根据路径自动分类——界面、样式、依赖、配置——所以翻历史记录的感觉，像是在翻你自己这个下午干了什么。

**拍快照几乎不花钱。** 内容寻址存储加上 stat 缓存，意味着一次快照的边际成本只是**真正变化的那几个字节**。5000 个文件的项目，一次快照是个位数毫秒。这才是「每次保存都拍快照」能落地的原因，否则你第二天就会把它关掉。

**撤销永远可以再撤销。** 每次回滚之前都会先拍一张安全快照。不存在任何一串 timeloom 命令能让你丢失工作。

**它说中文。** 摘要、时间、健康状态都有中文。终端表格在中文下也是对齐的——这事听起来很小，直到你用过一个对不齐的工具。

## 命令一览

### 开始用

| 命令                       | 作用                               |
| -------------------------- | ---------------------------------- |
| `timeloom init`            | 开始跟踪当前文件夹                 |
| `timeloom watch [--ui]`    | 监听改动并自动拍快照，让它一直跑着 |
| `timeloom restore healthy` | 退回到上一个健康检查通过的版本     |

### 查看

| 命令                            | 作用                                      |
| ------------------------------- | ----------------------------------------- |
| `timeloom status`               | 这个项目现在什么情况                      |
| `timeloom list [-n 20] [--all]` | 最近的快照                                |
| `timeloom show <ref>`           | 某个快照里有什么                          |
| `timeloom diff [from] [to]`     | 比较两个快照，或者拿快照和当前文件比      |
| `timeloom check [ref]`          | 立刻跑一次健康检查并记录结果              |
| `timeloom why <path>`           | 解释某个文件为什么被跟踪 / 为什么没被跟踪 |

### 保存和回滚

| 命令                                         | 作用                                       |
| -------------------------------------------- | ------------------------------------------ |
| `timeloom snap [-m "名字"]`                  | 立刻拍一张快照                             |
| `timeloom restore <ref> [--dry-run] [--yes]` | 把文件退回到某个快照                       |
| `timeloom label <ref> <名字>`                | 给快照起名字，起了名字的永远不会被自动清理 |
| `timeloom pin <ref>` / `unpin <ref>`         | 永久保留某个快照                           |

### 维护

| 命令                         | 作用                   |
| ---------------------------- | ---------------------- |
| `timeloom prune [--dry-run]` | 清理旧快照             |
| `timeloom doctor [--deep]`   | 检查快照仓库有没有损坏 |
| `timeloom config [键] [值]`  | 读取或修改设置         |

### 怎么指定一个快照

所有需要 `<ref>` 的地方，下面这些写法都认：

| 写法       | 含义                       |
| ---------- | -------------------------- |
| `a1b2c3d4` | 完整 id，或者开头几个字符  |
| `latest`   | 最新的快照                 |
| `healthy`  | 最新的、健康检查通过的那个 |
| `~3`       | 往前数 3 个                |
| `"重构前"` | 你自己起的名字             |
| `#42`      | 序号 42                    |

## 它是怎么工作的

```
                  ┌─────────────┐
   文件变动 ─────▶│   监听器    │──┐  静默期 · 最长等待 · 定期重扫
                  └─────────────┘  │
                                   ▼
                  ┌─────────────────────────┐
                  │   扫描器 + stat 缓存    │  只重新计算变了的文件
                  └────────────┬────────────┘
                               ▼
      ┌────────────────────────────────────────────┐
      │      内容寻址对象库（sha256）               │  相同内容只存一份
      └────────────┬───────────────────────────────┘
                   ▼
      ┌────────────────────────┐      ┌──────────────────┐
      │   只追加的索引日志     │◀────▶│    健康探针      │
      └────────────────────────┘      └──────────────────┘
```

### 内容寻址存储

每个文件按内容的 SHA-256 存放，像 git 一样按前两位十六进制分片。一个文件出现在一千个快照里，也只存一份。对象带一个字节的编码标记，这样已经压缩过的资源（PNG、WOFF2）会跳过毫无意义的 deflate——对这类文件压缩只会让它**更大**。

读取时默认校验哈希。回滚是唯一一个「悄悄把损坏的字节写进你的工作文件」不可原谅的操作，而一个存活几个月的仓库出现位翻转并不是什么理论问题。

### stat 缓存，以及它带来的那个坑

大小和 mtime 都没变的文件不会被重新读取。这是一次快照花 40 毫秒还是花好几秒的区别。

但它也引入了 git 里那个著名的 "racily clean" 问题：**同一个文件系统时间戳刻度内被改了两次、且最终大小相同**的文件，光看 stat 是没法和没改过的文件区分开的。timeloom 的处理是：扫描边界前两秒内被碰过的文件一律当作脏的。代价是重新计算一遍你刚编辑过的那些文件——而那本来就是需要计算的那一批——换来的是彻底消灭「快照悄悄记录了过期内容」这一类 bug。

### 只追加的索引

快照记录写进日志，而不是重写一个文档。因为快照是在你工作时定时发生的，写入路径必须是崩溃安全的：一个写了一半的 JSON 文档会把你**整个历史**带走，而一条撕裂的日志末行只损失一个快照。打开时重放日志，冗余积累到一定程度再压实。

### 健康探针

配置的命令带真正的超时和真正的**进程树击杀**——POSIX 上给进程组发负 pid 信号，Windows 上用 `taskkill /T`。因为 `child.kill()` 只杀掉 shell，你的构建工具会永远跑下去。

结果区分四种情况，因为它们对你的意义完全不同：`能跑`、`跑不起来`（你的代码构建失败）、`检查超时`、`检查没跑成`（探针本身启动不了，通常是命令写错了）。把后两种混为一谈，会让 timeloom 在你打错一个字之后，默默把每个快照都标成坏的。

### ignore 匹配器

从零实现的完整 gitignore 语义：`!` 否定且后匹配优先、`**` 出现在开头/结尾/中间三种位置、字符类、锚定规则，以及嵌套 `.gitignore` 的分层——深层的覆盖浅层的。规则按所属目录分桶，匹配一个路径只会碰到那几条**可能适用**的规则，而不是遍历整个项目的规则。

`timeloom why <path>` 会告诉你到底是哪个文件里的哪一条规则决定了这个文件的命运。

## 配置

设置在 `.timeloom/config.json`，用 `timeloom config` 改：

```bash
timeloom config health.command "npm run build"
```

```bash
timeloom config watch.quietPeriodMs 5000
```

| 键                               | 默认值    | 控制什么                                           |
| -------------------------------- | --------- | -------------------------------------------------- |
| `health.command`                 | 自动检测  | 判断一个快照「能不能跑」的命令                     |
| `health.timeoutMs`               | `120000`  | 探针最多跑多久                                     |
| `health.minIntervalMs`           | `60000`   | 两次探针之间的最小间隔                             |
| `watch.quietPeriodMs`            | `3000`    | 文件安静多久之后才拍快照                           |
| `watch.maxWaitMs`                | `45000`   | 不管多忙，超过这个时间也要拍一张                   |
| `watch.reconcileIntervalMs`      | `300000`  | 全量重扫间隔，兜住监听器漏掉的事件                 |
| `maxFileBytes`                   | `5242880` | 超过这个大小的文件不跟踪                           |
| `ignore`                         | `[]`      | 额外的 gitignore 风格规则，优先级高于 `.gitignore` |
| `useGitignore`                   | `true`    | 是否遵守项目自己的 `.gitignore`                    |
| `retention.keepAllWithinMinutes` | `60`      | 这个时间内的快照全部保留                           |
| `retention.hourlyForHours`       | `24`      | 然后每小时留一个，留这么久                         |
| `retention.dailyForDays`         | `14`      | 然后每天留一个                                     |
| `retention.weeklyForWeeks`       | `8`       | 然后每周留一个                                     |
| `retention.maxSnapshots`         | `2000`    | 硬上限                                             |
| `server.port`                    | `7317`    | 网页界面的端口                                     |
| `language`                       | 自动检测  | `en` 或 `zh-CN`                                    |

清理策略是分层的，跟备份轮转一个思路：**分辨率随时间衰减**。五分钟前的东西你想要每一次改动；三周前的东西你只想要「那前后的某个版本」。

## 网页界面

```bash
timeloom watch --ui
```

会打印一个网址。页面上有时间线、哪些快照构建通过、diff 查看器、一键回滚，通过 SSE 实时更新。

背后的 API 文档在 [`docs/http-api.md`](docs/http-api.md)，接口足够稳定，可以拿来自己做界面。

### 为什么这个本地服务器要锁这么死

一个能删你源代码的本地服务器一直开着，是件挺严肃的事。四道互相独立的防线，因为任何单独一道都可能被绕过：

1. **只绑定回环地址**，在配置校验阶段就强制。非回环的 `host` 直接被拒绝，服务器从网络上根本摸不到。
2. **校验 Host 头**。防的是 DNS rebinding：攻击者的域名重新解析到 `127.0.0.1`，然后他的页面就以同源身份跟你说话。
3. **校验 Origin**。任何跨源请求一律拒绝。
4. **每次运行随机生成的 token**，常数时间比较，所有 `/api` 请求都必须带。界面拿到 token 的方式是服务端注入到它自己返回的那个页面里——所以其他源的页面拿不到；而且因为我们从不发送任何 CORS 头，它们也读不到响应。

token 不是用来防你自己机器上其他进程的。以你的身份运行的程序本来就能直接读你的项目，那里没什么可防的。

## 安全和隐私

**没有任何数据离开你的机器。** timeloom 不发起任何网络请求。没有遥测，没有账号，没有云。

**`.timeloom/` 里是每个被跟踪文件的每一个版本的完整副本**——包括你的 `.env`（如果有的话）。两道机制防止你把它传上去：`init` 会把 `.timeloom/` 追加到你的 `.gitignore`；同时仓库目录里自带一个内容为 `*` 的 `.gitignore`，**哪怕你的项目根本没有 .gitignore 也照样生效**。

提 issue 的时候，**不要粘贴 `.timeloom/` 里的内容**。

完整策略见 [`SECURITY.md`](SECURITY.md)。

## 零依赖是刻意的

`npm install timeloom` 只会装 timeloom，别的什么都不装。没有传递依赖树，没有 audit 报警，没有安装时的意外。

这是要付出真实代价的——gitignore 匹配器、命令行参数解析、HTTP 服务器、终端字符宽度计算全都是手写的。换来的是两件对这个用户群特别重要的事：**新手接触一个工具的第一步，不该是安装失败**；以及，一个卖点是「你的文件很安全」的工具，没有任何理由往存着这些文件的机器上拖三百个包。

## timeloom 和 git 的关系

它们不是二选一。timeloom 是你工作目录下面的安全网，git 是你发布和协作的方式。

|                      | timeloom             | git                         |
| -------------------- | -------------------- | --------------------------- |
| 谁决定什么时候保存   | 它自己，自动的       | 你                          |
| 知不知道某个版本能跑 | 知道，它会跑你的构建 | 不知道                      |
| 上手需要什么         | 什么都不需要         | 得懂 commit、branch、暂存区 |
| 适合干什么           | 撤销刚才这一小时     | 历史、协作、发版            |
| 该不该两个都用       | 该                   | 该                          |

如果你已经在用 git，timeloom 填的是**两次提交之间的那段空白**——你正想到一半、因为还没做完所以没提交的那几个小时。

## 在代码里调用

```ts
import { Repository } from 'timeloom';

const repo = await Repository.open(process.cwd());

await repo.snapshot({ trigger: 'manual', label: '重构前' });
await repo.restore('healthy');

const status = await repo.status();
console.log(status.lastHealthy?.id);
```

CLI 能做的每一件事都走这套 API。编辑器插件和自定义面板是它预期的使用者。

## 常见问题

**这个能替代 git 吗？**
不能，见上面那张表。两个都用。

**会不会让我电脑变卡？**
快照是增量的，通常几毫秒。健康探针会跑你的构建，那部分该多久就多久，但它有频率限制，而且一旦结果过期就立刻取消。

**占多少磁盘？**
大致是项目大小，加上这段时间里变化过的字节。`timeloom status` 会告诉你确切数字，`timeloom prune` 可以清理旧历史。

**万一它漏掉了某次改动？**
递归文件监听器在高负载和网络盘上确实会丢事件。timeloom 正是为此每五分钟做一次全量核对扫描；如果递归监听在当前环境完全不可用，它会退化成纯定期扫描而不是直接失败。

**能跟踪 `.env` 吗？**
默认是跟踪的，因为误删 `.env` 是很常见也很痛的错误。仓库目录有两道独立机制挡住 git。如果你不想跟踪，把 `.env` 加到配置的 `ignore` 里。

**提示有损坏怎么办？**
`timeloom doctor --deep` 会逐个校验每个存储对象的哈希，告诉你哪些快照受影响。较新的快照通常不受波及。
